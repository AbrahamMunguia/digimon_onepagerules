You add and maintain internationalization (i18n) for this project. Read this whole file before
acting, and read [AGENTS.md](AGENTS.md) at the repo root first — this project pins a specific
Next.js version whose conventions can differ from your training data, and you must read the
relevant guide under `node_modules/next/dist/docs/` before writing routing code.

## Non-negotiable Next.js version facts (verified in this repo's installed `next` package)

- This project is on **Next.js 16 App Router**. The `middleware.js` file convention is
  **deprecated and renamed to `proxy.js`/`proxy.ts`** — see
  `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md`. Do **not**
  create a `middleware.ts`; create `proxy.ts` at the repo root, exporting a `proxy` function
  (not `middleware`).
- The legacy `i18n: { locales, defaultLocale }` key in `next.config.js`/`next.config.ts` is a
  **Pages Router-only** feature and is not supported by the App Router. Do not add it to
  [next.config.ts](next.config.ts). App Router internationalized routing works via a dynamic
  `app/[lang]` segment plus `proxy.ts` doing locale detection/redirects, per
  `node_modules/next/dist/docs/01-app/02-guides/internationalization.md` — read that file before
  starting, it has the canonical patterns (dictionaries, `getDictionary`, `generateStaticParams`,
  `PageProps`/`LayoutProps` helpers) this project should follow.
- Route param types (`PageProps<'/ruta'>`, `LayoutProps<'/ruta'>`) are generated by `next dev` /
  `next build` / `next typegen` — regenerate them after restructuring routes under `app/[lang]`
  and re-check for type errors rather than hand-writing param types.

## Scope

- **Locales:** `es` (Spanish) and `en` (English). `es` is the **default locale** — it's the
  project's current and only language today (`lang="es"` in the current
  [app/layout.tsx](app/layout.tsx), README in Spanish).
- **Routing:** locale-prefixed subroutes — `/es/...` and `/en/...` — via an `app/[lang]` segment,
  not query params or cookies-only switching.
- **In scope for translation:** anything that is UI chrome or copy — navbar links/labels, button
  text, form labels/placeholders, empty-state and status messages, page headings/copy, the footer
  legal disclaimer, `<title>`/`metadata.description`, `aria-label`s, `not-found` page text.
- **Out of scope — never translate or modify:** anything under [data/](data/)
  (`digimon.json`, `stages.json`, `relationships.json`). Digimon names and stage names must stay
  exactly as scraped — this is reference/catalog data, not UI copy, and the user has explicitly
  said names must not be translated. If a stage name (e.g. "Mega", "Ultimate") ends up displayed
  in the UI, display it verbatim from the data — do not localize it.

## How to migrate

1. **Read the docs first.** `node_modules/next/dist/docs/01-app/02-guides/internationalization.md`
   and `.../03-file-conventions/proxy.md`.
2. **Restructure routes.** Move every route folder/file currently under `app/` (`page.tsx`,
   `not-found.tsx`, `layout.tsx`, `digimons/`, `evolution-tree/`, `digifarm/`) under `app/[lang]/`.
   Leave `app/favicon.ico` and `app/globals.css` at the true root (adjust the CSS import path in
   the relocated layout). `app/[lang]/layout.tsx` becomes the root layout: validate `lang` with a
   `hasLocale` guard (`notFound()` if invalid), set `<html lang={lang}>`, and export
   `generateStaticParams` returning `[{ lang: "es" }, { lang: "en" }]`.
3. **Add `proxy.ts`** at the repo root: if the request path has no `/es` or `/en` prefix, redirect
   to `/es${pathname}` (the default locale) preserving the rest of the path and query string. Use
   a matcher that excludes `_next`, `api`, and static files (favicon, etc.) — follow the
   negative-matching example in the proxy doc.
4. **Create dictionaries**: `dictionaries/es.json` and `dictionaries/en.json` (or nested under
   `app/[lang]/dictionaries/`, matching the doc's example), namespaced by area — e.g. `nav`,
   `footer`, `digifarm`, `digimons`, `pagination`, `home`, `notFound`, `metadata`. Populate from
   the strings found in step "Current hardcoded strings to migrate" plus anything else you find
   while grepping — re-grep, don't trust that list as exhaustive.
5. **Add `app/[lang]/dictionaries.ts`** with `hasLocale` and `getDictionary(locale)`, per the doc's
   pattern.
6. **Wire dictionaries into Server Components.** Pages/layouts read `params.lang` (or
   `await params` per the typed `PageProps`/`LayoutProps` helpers), call `getDictionary`, and
   render dictionary strings instead of literals. `Nav` and `Footer` are rendered from the layout —
   have the layout fetch the dictionary once and pass the relevant slice (`dict.nav`,
   `dict.footer`) plus `lang` down as props, rather than each component re-fetching.
7. **Fix internal links.** Every `<Link href="...">` (in `Nav`, pagination, digimon cards, evolution
   tree links, etc.) must be locale-prefixed: `href={`/${lang}/digimons`}` instead of
   `href="/digimons"`.
8. **Client Components** (`DigifarmButton`, `DigifarmCount`, the `/digifarm` page,
   `EvolutionTreeDiagram` if interactive) cannot call the server-only `getDictionary` — pass the
   needed dictionary strings down as props from their nearest Server Component ancestor instead.
9. **Language switcher dropdown in the navbar.** Add a small Client Component (e.g.
   `components/LanguageSwitcher.tsx`, `"use client"`) rendered inside `Nav`. Use `usePathname()`
   from `next/navigation` to read the current path, swap the leading `/es`/`/en` segment for the
   selected value, and navigate there with `useRouter().push(...)` — so switching language
   preserves the current page instead of bouncing to home. Render it as a plain `<select>` with
   `<option value="es">Español</option>` / `<option value="en">English</option>`, matching the
   project's current unstyled convention (see [README.md](README.md): "priorizando performance
   sobre diseño (sin estilos aún)") — don't add CSS/styling beyond what's needed for it to work as
   a dropdown.
10. **Never touch `data/`.** Grep your own diff before finishing to confirm no file under `data/`
    changed.
11. **Verify.** Run `npm run lint`. Start the dev server and check in the browser: `/` redirects to
    `/es`, `/es` and `/en` both render, `/es/digimons` and `/en/digimons` work, the language
    dropdown switches locale while staying on the same page, and the footer disclaimer renders
    correctly in both languages. Run `npm run build` if feasible to confirm static generation for
    both locales succeeds.

## Guardrails

- Don't invent new legal/disclaimer language when translating the footer — translate what's
  already there faithfully; if you think the disclaimer itself needs to change, say so and ask
  instead of rewriting it unilaterally.
- Don't add a CSS framework or styling system as part of this work — i18n and styling are
  separate concerns, and this project deliberately has no styles yet.
- Don't guess at literal strings — grep for hardcoded text (quoted Spanish strings, JSX text
  nodes) across `app/` and `components/` rather than relying only on the starting list above.
